# Code Guidelines

## Comments

- All comments should be concise but also include all information needed to understand the implementation logic.
- All functions should contain comments over it to describe its usage and purpose.
- If the parameters and return values of a method are not clear from the definition, add comments before the method explaining them. Follow language specific format.
- Write comment before every 2/3 lines of code detailing what it does. The comments should help a new engineer understand the project easily who may not know the modules or methods used. Don't explain language syntaxes. Assume the new engineers knows the programming language well, so don't explain codes that do not use any methods or libraries.
- For DB tables, write comment for each column unless it's obvious like ID, timestamps etc.

## File and Folder Structure

- A file should only contain related functions/classes.
- A file should only contain one main class and smaller helper class that depends on the main class. This applies to ORM models and Controllers/ViewSets too.
- A file should only contain related methods.
- Multiple related classes or models should be grouped in a single folder.
- If there are multiple similar files like multiple routers, controllers, services etc for the same module/app, then they should be grouped in a folder.
- Try to keep the file length less than 300 lines, unless the methods are really related and will cause confusion if refactored.
- Use proper versioning.

## Code Structure

### Core Code Rules

- Encapsulate all related methods in a class. Use static methods with a singleton class when the methods are independant like Services.
- You may write methods outside of classes for small utilities that doesn't make sense to put in a class.
- Try to divide work into small helper methods for better readability. If the helper methods don't need to exported, make them private. All methods that do not implement business logic and doesn't need to be exported/imported are helper methods.
- Keep all helper methods at the bottom of the class with a divider line before they start.
- Try to keep function length under 30 lines.
- Keep the codes modular and reusable. Don't repeat same code.
- Apply formatting with the default formatter for IDE after modifying a file. Skip if there's no default formatter configured.

### Environment Variables

- Group related environment variables together and write comments.
- Create .env.local.example and .env.production.example
- .env.local.example should be ready for dev environment so that `mv .env.local.example .env` is enough to start the dev environment.
- .env.production.example should have dummy values or descriptions like MY_SECRET=<Generate 32+ chars secret using command `openssl rand -hex 32`>
- For monorepos, the env file names should have the app name in the file name like - `.env.auth_api.local.example`.
- Common environment variables should be top level and the rest should be inside their respective repos.
- When deploying using docker compose, Kubernetes, or GitHub Actions, respect the seperation of env files and don't put all the variables in a single production env file.
- Versions, Service/Package name, title, and other software informations SHOULD NOT BE IN ENVIRONMENT VARIABLES.

### Config files
- The config folder should contain the config files.
- All configurations that do not relate to deployment should be in config files.

### Docker/Kubernetes

- In Docker Compose or Kubernetes files, write long syntaxes for clarity.

## Implementation Guide

- Always prefer UUID to be generated by DB instead of the Application UNLESS multiple objects need the same ID before persistence.
- A single migration file should not contain changes to more than one table UNLESS a change in feature requires small changes to multiple tables together, in which case, you may write changes to multiple tables in a single migration.
- Implement CQRS - Query files will query DB and Repositories will mutate DB. No other files in the project should query or mutate DB data.
- Repositories only handle ORM calls or execute SQLs and return the data. - Repositories shouldn’t know about any DTO, it should return the data as it comes from the ORM. It shouldn't commit.
- Query or Repository shouldn't have any logic other than using ORMs/SQLs.
- Services should contain the core business logic and is responsible for persistence. So services will commit DB changes, but will use Query to get DB data and Repository to mutate DB data.
- Services should return data in DTO formats.
- Use Factory pattern when applicable.

### Python

- Follow PEP8 naming conventions.
- Use UV for package management.

### Express.js

- Routers should only define routes to controllers, containing no functions.
- Controllers should only validate and call services, containing no business logic.

### Django

- Follow Django's app based file structure. DON'T FOLLOW ONION/CLEAN ARCHITECTURE.
- ViewSets should only validate and call services, containing no business logic.
- Each domain database model should have it's own app.
- Use custom manager to encapsulate common and core database queries and pre-filter table-level operations.
- Break settings file into multiple. Group related settings together. Main settings files are development, production, and test. A folder named base should contain base setting files where related settings are grouped together.

### FastAPI

- Follow Onion Architecture.
- Routers should only define routes to controllers, containing no functions.
- Controllers should only validate and call services, containing no business logic.
- Dependency methods should be in its own file.
- For authorization, use Policy classes similar to Ruby on Rails.
- Use file names like `_router.py`, `_controller.py`.
- If there is user authentication, then request.state.user should contain the user information.
- If there is multi-tenancy, then request.state.tenant should contain the tenant information.
